Answers to the syscall lab questions (gdb experiments performed on this machine,
xv6-labs-2025, branch `syscall`, commit 63d40cb).

Q1: (gdb) b syscall, continue, then backtrace -- which function called syscall()?

A1: usertrap() called it, from kernel/trap.c:68.
The backtrace is:
  #0  syscall () at kernel/syscall.c:159
  #1  0x... in usertrap () at kernel/trap.c:68
  #2  0x... in uservec () at kernel/trampoline.S:...
usertrap() is the only place in the kernel that calls syscall(): it is entered
via the trap path (ecall from user mode -> stvec -> uservec -> usertrap), and
when scause == 8 (environment call from U-mode) it dispatches to syscall().

Q2: What is the value of p->trapframe->a7 and what does that value mean?

A2: a7 = 7. a7 carries the system call number, placed there by the user-space
stub generated by usys.pl ("li a7, <num>; ecall"). Number 7 is SYS_exec
(kernel/syscall.h:8). This is expected: the very first system call made by the
first user process is exec("init", argv) in user/init.c, which loads a7 = 7
(visible in user/init.asm as "li a7,7").

Q3: p /x $sstatus -- what does this tell you about the previous mode?

A3: The SPP bit (bit 8) of sstatus is 0, which means the trap came from
U-mode (user mode). SPP holds the privilege mode the hart was in before the
trap; 0 = User, 1 = Supervisor. So at the breakpoint inside syscall() we can
confirm the hart was executing a user process (init) before the ecall trapped
into the kernel.

Q4: With "num = *(int*)0;" injected in syscall(), the kernel crashes.
What instruction (in kernel.asm at the sepc address) is the faulting
instruction? Which register does num correspond to?

A4: The panic prints: scause=0xd sepc=0x80001cfc stval=0x0
At sepc = 0x80001cfc, kernel/kernel.asm shows:
    80001cfc:   00002903    lw  s2,0(zero)   # 0x0
i.e. the faulting instruction is a "lw" (load word) from address 0 (computed
as 0(zero), the zero register). The compiler placed num in register s2, so
num corresponds to s2. (Address 0 of the load is not a "real" pointer -- the
C expression *(int*)0 was compiled into a load from the zero register.)

Q5: Why did the kernel crash? Hint: how is a kernel virtual address
translated to a physical address?

A5: Virtual address 0 is not mapped in the kernel page table. The kernel's
page table (kernel/kernel.c: kvmmake()) only maps:
  - a trampoline page at the very top (TRAMPOLINE),
  - the kernel text/data at KERNBASE (0x80000000) and above,
  - device MMIO regions (UART, VIRTIO, PLIC, CLINT) around 0x0c000000-0x10008000.
Address 0 has no PTE, so the "lw s2,0(zero)" causes a load page fault
(scause = 13 = 0xd, stval = the faulting address 0). The CPU traps to
kerneltrap(); the fault is not a device interrupt (devintr() returns 0) and
the trap did not come from user mode, so kerneltrap() falls through to
panic("kerneltrap"), which halts the kernel. This is exactly the point of
the experiment: the kernel cannot dereference arbitrary addresses -- only
addresses present in its page table (which is why user pointers must go
through copyin/copyout, and why argstr() copies strings from user space).

Q6: What is the name of the process that triggered the crash? What is
its pid?

A6: The process is "init", pid 1.
Observed in gdb by breaking at the faulting instruction before it executes:
  (gdb) b *0x80001cfc
  (gdb) c
  Thread 2 hit Breakpoint 1, syscall () at kernel/syscall.c:196
  (gdb) p p->pid
  $1 = 1
  (gdb) p p->name
  $2 = "init", '\000' <repeats 11 times>
This is init because it is the first user process ever started (spawned by
the kernel), and its first system call (exec) is the first one to reach
syscall(), so it is the first victim of the injected bug.
